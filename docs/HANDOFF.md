## 1. 用户到底要什么

不是"帮我加一条记录"（他自己点两下就行）。真实场景是：

> **跟我一起把计划聊出来，然后把整份计划排到桌面日历上，并用一套稳定的视觉语言让人一眼看懂。**

所以工作流是：**聊 → 我出清单表 → 他改 → 批量写入 → 重启日历一次 → 回读核对**。

## 3. 日历数据模型（已验证）

| 表 | 我们 |
|---|---|
| `item_table` | **读写**：每天格子的文字（`it_content`，纯文本 + 可选 `<font>`）、格子底色（`it_bgcolor`） |
| `event_table` | **只写两类**：提醒 `ev_type=2`、倒数日 `ev_type=3`；**`ev_type=1` 绝对不写**（用户明确否决，那是"非文字形式的每日条目"） |

铁律：

- `ev_start_date` 必须带毫秒 `2026-12-10T00:00:00.000+0800`，少 `.000` → 条目只在底部提示框、**不进格子**
- `ev_status` 必须 `1`；写 `2` 会变成"完成/无状态"，这是早期翻车的根因
- `ev_unique_id` 用标准格式 `event-YYYYMMDD-HHMMSS-mmm-0`
- `ev_reminder` 是**从当天 0 点算起的 ISO 时长**：`P0DT13H30M0S` = 当天 13:30（不是 `13:30` 字符串）
- 底色 `it_bgcolor` 是 **BGR**、不带 `#`：`#722F37` → `372F72`（用像素采样验证过）
- 文字色是标准 `<font color="#RRGGBB">`（RGB）
- 自定义转义：`" < >` 各包一层 `|X|` 再 HTML 转义；`it_content` 本身不编码
- 存文件一律 UTF-8；**不要用 PowerShell `ConvertTo-Json` 回写**（会把中文变 `??`，踩过一次）

## 4. 颜色 / 视觉模型（用户逐步定的）

- **文字色 = 这件事的身份**（一个项目一个颜色；待办/提醒/倒数日共用）
- **底色 = 截止日**：只在截止那天铺，证明"到这天要完成"
- 只有两种形态：**截止型**（有 deadline）/ **非截止型**（无，永久占用）
- **不存开始时间**——日历只排未来的事，类目的开始恒等于"现在"
- 撞色判定分两层：
  - 建新类目/挑色：`ongoing` 永远占用；`project` 占到 `deadline`
  - 写某天条目：用**条目日期 D** 比，`D > deadline` 才能借这个颜色
- 归档：`deadline < 今天` 自动挪进归档表，**活跃表永远只有几条**（省 token/算力，用户特别强调）
- 未归类的事 **不上色**（颜色=身份，没身份就没颜色）

## 5. 面板（两处入口，同一份数据）

- **DSH 右侧栏**：顶栏右上角日历图标 → tab「CalendarTask」；「开始」页也有卡片
- **浏览器**：`http://localhost:8777`（兜底）

特性：即时保存（无全局保存按钮）、改色要点「确认」、撞色前后端双校验（409 回滚）、进行中/已归档两个页签、日期格式 `dd/Mon/yyyy`、没截止日显示 `∞`。
服务由插件在启动时**自动拉起**（Host 半 `index.js` 里 `ensureServer()`）。

### 交互模型（用户定的，别改回去）

> "配置收起的时候，我们除了拖动摆放什么也干不了；单项设置展开以后，才可以选它的颜色、日期、编辑它（包括删除）。"
> "色板还有日历做成左右结构…颜色可选项给出来更多一点。最下面是确认和删除，不要收起。"

| 状态 | 能做什么 | 不能做什么 |
|---|---|---|
| **收起**（默认） | 展开这一条；拖把手改顺序 | 改名、改色、改日期、删除——**入口一个都不许露在行上** |
| **展开**（一次一条） | 卡片里改名称、选颜色、选截止日，底部「确认」落盘 /「删除」删掉 | 拖动（展开时把手 `draggable=false`，顺序只在收起态整理） |

**卡片内部布局**：名称（整行输入框）→ 下面左右两栏（左「颜色」22 格 DesktopCal 色板 + 选色行 + 内联取色器，右「截止日」月历）→ 底部 `× 删除` / `确认`。

踩过的坑：
1. 第一版把入口摊在行上——名称是常驻输入框、删除是 hover 显形的 `×`、颜色和日历各弹一块在行下面，用户直接说"散落在各处"。**再加任何单条目的设置，都放进 `.ctp-edit` 那张卡里，别往行上挂。**
2. 第二版把颜色和日历上下堆着，用户要左右并排；并排后日历必须收紧（格子 26px 高、字号 12）才塞得下半个侧栏。
3. **卡片编辑是草稿制**：改动只进 `draft`，点「确认」才写盘。点行头或 Esc 收起 = 丢弃草稿（`title` 上写了"不保存改动"）。底栏是 `删除`（仅已有条目）+ `取消` + `确认`。
4. **新增也是草稿，不落库**。点「新增事项」只在本机起一条 `newItem`（`open === -1`），行会出现在第一行但**登记表一个字都没写**；点「确认」才 `commit` 落盘，点「取消」整条消失。**别再改成"新增即保存"**——用户明确否掉了，之前那样点完新增什么都没选也会存一条空记录。
5. **名称必填**（用户定的）：新增和修改都一样，空名字（含纯空格）不许落盘。三处一起挡着——「确认」按钮 `disabled`、名称标签右边显示红色「必填」、`confirmEdit()` 里 `trim()` 后再判一次；服务端 `_validate()` 也会返回 409，防止别的入口绕过去。**注意**：现在"只填了颜色没填名字"点不了确认，这是有意的。

实现要点：
- 行是 `role="button" tabIndex=0`，点/回车/空格切换展开，Esc 收起；`data-open` 驱动样式
- 展开时**行头显示草稿值**（`shown = isOpen && draft ? draft : it`），所以选色后头部立刻变色，取消又变回去
- 排序列 = `items` 数组顺序，拖完直接 `commit(next)` 落盘（没有单独的 order 字段）；**排序是即时保存的**，只有卡片里的字段要确认
- 拖动只用把手的 HTML5 DnD（`dragstart/dragover/drop`），落点用 `data-over` 画一条 `inset 0 2px` 的蓝线；`dragleave` 要判 `contains(relatedTarget)`，否则行内移动会闪
- 十六进制输入是**即时校验**：合法且没被占就改草稿，不合法/被占就在下面出红字（`data-bad` + `.ctp-hexerr`），不再有单独的"确认"按钮
- **色板三页签，尺寸全部写死**（用户反复强调的点）：格子 `24×24`、`repeat(8,24px)`、间隙 4 → **定宽 220px**
  - 「CalendarTask」页 = DesktopCal 的 22 色，按 **7 / 7 / 8** 排三排，空位留在每排末尾——位置由内联 `gridRow/gridColumn` 指定，所以**不能用 `grid-auto-flow` 自动排**
  - 「Windows」页 = 系统 48 格，8 列 × 6 排自动排（这页没有空位）
  - **别换回 `flex-wrap` 也别用 `1fr` 格子**：前者行数随宽度变，后者高度随宽度变，两种都被否掉了
- **卡片高度定死在 `--palette-h:259px`**（`.ctp-duo{min-height:…}`），也就是三页里最高的那页（Windows 48 格）撑出来的高度。定死是为了**切页签时卡片不跳、右边日历不伸缩**。实测三页 `duo` 都是 259、日历 234、卡片 413.8、底边都在 630
- **右栏底边必须跟左栏对齐**（用户要的"日历高度 = 取色器高度"，指的是两栏**整体**等高，不是"色板块和日历块各 220"）。做法：`.ctp-duo` 用 **flex + `align-items:stretch`**；右栏 `.ctp-sec` 里把标题和 `.ctp-cal` 都**绝对定位**（`top:25px;left:14px;right:0;bottom:0`），这样右栏高度只能由左栏决定，不用猜日历内容多高
- **坑：`.ctp-sec` 自带 `margin-bottom:14px`**（给"名称"那节留的），它会让左栏少 14px、两栏差一截。`.ctp-duo > .ctp-sec` 必须显式 `margin:0`
- **坑：别用 grid 的 `align-items:stretch` 做这件事**——实测同一行里左栏 278、右栏 292，拉伸没生效；换 flex 才正常
- **坑：绝对定位 + `width:100%` 会溢出**。日历块用 `left:14px;right:0` 定位时不能同时留 `width:100%`——宽度会按父级算，比 right 边界多出 14px（用户一眼看到"右边溢出"）。宽度交给 left/right 就好
- **两栏之间那条竖线**：`.ctp-duo::before`，`left:227px`（220 列 + 14 gap 的中线）、`top:25px`、`bottom:0`、`background:var(--line)`——跟"确认/删除"上方那条横线同色同粗细，底边跟着两栏一起对齐
- 布局是"色板定宽 + 日历吃掉剩下的"：`.ctp-duo` 是 flex，`:first-child{flex:0 0 220px}`，日期格宽度随列宽伸缩
- **整张单子限宽 640 居中**（`.ctp-inner`）。原因：七列月历在 840 宽的面板里若铺满，日期格会变成 87×26 的宽条，比留白更难看；限宽后是 57×26。想改就调 `.ctp-inner` 的 `max-width`，但再宽日期格就开始变形
- **窄宽兜底**：`@container (max-width:420px)` 时两栏退回上下堆叠、隐藏竖线、色板铺满整行（`repeat(8,minmax(0,1fr))`）。**容器查询必须放在样式表最末尾**，否则会被后面的基础规则覆盖（踩过）
- **坑：页签内容高度不同 → 必须给 `.ctp-duo` 定 `min-height`**。不定的话切到矮的那页，左栏塌、右栏 `bottom:0` 跟着塌，日历整块被压扁、日期数字叠成一团（`check_design` 曾报过 9 处"文字叠在一起"）
- 底部两个按钮同款只差颜色：`data-v="primary"`（黑 `--ink`）/ `data-v="danger"`（红 `--danger` #B42318，hover #9A1D13），同尺寸 ~53×30

**颜色这一块的实现**（`client.js` 的 `ColorField` + `WinPicker`）：
- 三个页签：`CalendarTask`（22 色）/ `Windows`（48 格）/ `自定义`（同规则取色器）
- **hex + 释放色那一行统一贴左栏底边**（`.ctp-duo > .ctp-sec:first-child > .ctp-colorrow{margin-top:auto}`）。三页签实测 `top` 都是 536、`bottom` 都是 562、离左栏底边 0 —— 切页签它不上下跳（用户要求的）。多出来的空白因此落在色板和这一行之间
- **右边固定留 5 格**（`flex:0 0 132px` = 24×5 + 3×4）：装的是下面说的「归档释放色」。不足 5 个时右边留着当富余，不往回挤 hex（实测 0/1/4 个时 hexW 77 / recentW 132 / 行 21→241 都不变）
- **释放色的色块 20×20，跟色板格子一模一样**：`.ctp-mini` 是 24×24 按钮 + 2px 内缩（色板 `.ctp-sw` 也是 24×24 + 2px），可见方块和描边都对齐（实测两边 span 都是 20）
- **两套色板必须分页**：交集是 0，但有几对非常接近（`#4A0081`/`#400080` 差 10、`#FBF078`/`#FFFF80` 差 17.5、`#009300`/`#008000` 差 19），混在同一格里迟早点到"看着一样、其实是两个值"
- **不再用任何第三方取色器组件**。原来内联过 react-colorful 5.6.1（13.7KB，MIT），换成同规则的 `WinPicker` 之后整块删掉了，`client.js` 反而更短
- `WinPicker` 三块，全部照那个系统对话框的规则：
  - **平面**：`<canvas>` 200×96，**永远画 `L=50%` 的 色相×饱和度**——它那个对话框就是这样，平面不随亮度变；画一次就够（`createImageData` 一次填完）
  - **亮度竖条**：14×96，白→黑渐变，拖它改 L
  - **六格数字**：色相 0–239 / 饱和 0–240 / 亮度 0–240 / 红绿蓝 0–255，字段名和范围都跟它一致
- 数值口径：内部统一 `h 0-360 / s,l 0-100`，跟它接口的地方换成 Windows 口径（H 乘 `240/360`，S/L 乘 `2.4`）。**照它是为了在它那边能把数字直接抄过去**
- 取色器是连续值：拖动照常改草稿，被占用的只在下面给红字。**点色块 / 输 hex / 点释放色才硬拦截**（被占用就不让选）
- **右边 5 格 = 「归档释放出来的颜色」**（用户定的，替换掉了原来的「最近选过」）
  - 为什么换掉：「最近选过」只有把颜色**给出去**之后才会产生，而给出去的颜色恰好被别的条目占着 → 那排格子天然只会摆出"点不了的颜色"，结构上自相矛盾
  - 规则在 `server.py` 的 `released()`：归档数组**倒着读**（`tidy()` 是 `+ moved` 往后追加的，所以倒序 = 最近归档的在前），同一个颜色只留最近一次，**还被在役条目（未过期）占着的跳过**；前端再把「当前正在选的那个色」滤掉（用户要求：刚被重新选中的释放色就不显示，让后面别的补上来）
  - `/api/data` 多返回 `released: [{color, name, deadline}]`（最多 8 条，前端取 5）；色块的 title 是「条目名 · 截止日 归档后释放」
  - 已实测：在役占着同色的跳过、ongoing 条目永不释放、同色多次归档只留最近一次、空归档返回 `[]`
- 色板必须手写（不能拿通用取色器代替），因为只有它能把「这个颜色已经被谁占用」画在格子上（斜线 + 悬停说明）

### 视觉必须照设计稿走（`design/dc-panel/panel-a.html`）

**不要再拿行内样式写这个面板。** 行内样式表达不了 hover、行间分隔线（`::after`）、已占用斜线（`linear-gradient`）、焦点环——第一版就是这么被"简化"成一排紧凑小字的，用户一眼看出"跟设计不一样"。

现在的做法：整份样式是 `client.js` 里的 `CSS` 常量（全部收在 `.ctp` 作用域下），组件 `mount` 时插一个 `<style id="ctp-style">`，类名与设计稿一一对应（`.ctp-row` / `.ctp-due` / `.ctp-edit` …）。改样式改那个常量即可，不要再往 JSX 里塞 `style`。

宿主给的边界（从 `app.asar` 源码确认的，不是猜）：

| 事实 | 影响 |
|---|---|
| `.tabBody` = `flex column; height:100%; overflow:hidden`，**不加任何内边距** | 面板自己管 padding（`14px 12px 22px`）和滚动（`height:100%; overflow-y:auto`）；漏了滚动，事项一多就被裁掉且滚不动 |
| tab 正文直接是 `.tabBody` 的子元素（`<div class="tabBody">{content}</div>`），没有额外包裹层 | `height:100%` 能正常解析 |
| 面板可停靠可浮窗，宽度不固定 | 栅格用 `minmax(84px,110px)` 让日期列能收；抬头用"h1 + 按钮同行、说明另起一行"，否则窄了按钮会被挤到第二行 |
| 主题 `preference: light` | 面板可以固定浅色（`#FAFAF9`），不必跟深色变量 |
| **`require` 只认 11 个静态模块**：`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`、`@deepseek-ai/cordis`、`zod`、`@tanstack/react-virtual`、`@deepseek-ai/dsh-client-store`、`@deepseek-ai/dsh-client-ui-slots`、`@deepseek-ai/dsh-client-ui-primitives`、`@deepseek-ai/dsh-client-ui-dockkit` | 要别的库只能内联源码；`react-dom` 可用 → 能做 portal 浮层；`ui-primitives` 里**没有**取色组件（91+ 导出里只有 Button/Input/Menu/Modal/HoverCard/图标等），但有 `Modal`、`MenuSurface`、`useDismissOnOutsidePointer` 可复用 |

### 日期选择器：自己画的

**原生 `<input type=date>` 的弹层完全不可样式化**，CSS 只能改 `::-webkit-calendar-picker-indicator` 那个小图标，弹层本体（"December 2026"、Clear/Today 那一坨）是浏览器 UI，改不了。用户看过之后明确要换成面板自己的样式。

`app.asar` 里 DSH 自己有个 `@deepseek-ai/dsh-client-ui-schedule/src/client/DatePicker.tsx`（232px 卡、周一开头、CSS 锚点定位、方向键+Enter+Esc），但是：它**只存在于 asar 里，没装进 profile 的 node_modules**，插件 `require` 不到；插件也没有打包步骤，npm 上的日历/取色组件（react-day-picker、react-colorful）同样加载不了。**结论：能用的现成组件一个都没有，只能手写。**

现在 `client.js` 里的 `DateCard` 就是手写的月历卡（约 70 行），照 DSH 那个的尺寸来：28px 格子、22px 星期行、26px 翻页钮、7 号圆角，配色用面板自己的 token。行为：

| 交互 | 实现 |
|---|---|
| 点截止日 | 卡片就地展开（跟取色卡同一个套路，不弹层，避免被 `.ctp` 的 `overflow` 裁掉） |
| 翻月 | 左右箭头，切月时日号 clamp 到当月长度 |
| 键盘 | **只有 Esc 有效**（关卡片）。`STEP` 那段只改 `view.d`，但渲染根本没用到 `view.d`；也没有 Enter/空格选中 —— 方向键按下去没有任何可见反应。要补的话：用 `view.d` 画焦点框、Enter 调 `onPick(view.d)` |
| 今天 | 底部「今天」 |
| **去掉截止日** | 底部「不设截止日」→ `deadline: null`，`kind` 变 `ongoing`，颜色恢复永久占用（以前根本没有回 ∞ 的入口） |
| **过去的日子不能选** | 最早可选 = `max(今天, 这个颜色最后一条安排的日期)`。早于它的格子画斜纹、不可点；翻到那个月就不再往前翻（箭头置灰）；标题右边写「今天起可设」或「最早 X」。已经存在的、过去的截止日照常显示（红字提示"早于最早可选日"），否则编辑老数据时它在日历上会凭空消失 |

### 取色板：22 色照抄 DesktopCal，下面接一个常驻取色器

色板**不再是我们自己挑的 56 色**，而是 DesktopCal 日格调色板的 **22 色、顺序一致、位置一致**。原因：56 色里一半是它给不出来的颜色，用户在两边对不上号，手改就没法还原。

**色值来历（别凭印象改，也别换一种办法重取）**
- 它在日格取色器里是 **7 / 7 / 8** 三排：第一列上两格是「清除」∅ 和「调色板」两个图标（不是颜色），所以前两排只有 7 个色。我们不要那两个图标，空位留在每排末尾
- **13 个能逐字节核对**：`%APPDATA%\CalendarTask\app\dkappcal\resource.zip → config/res.xml` 里的 `richeditTextColorN`，存的是 COLORREF（`0xRRGGBB` 是 **BGR 序**：`0x2424F1` = `#F12424`、`0x9595FF` = `#FF9595`）。13 个全部对上
- **22 个色值全部在 `dkappcal.dll` 里逐字节坐实**（不是靠截图猜的）：`app\dkappcal\dkappcal.dll` 文件偏移 **0x211514** 是一张 23 项的 COLORREF 数组，顺序就是
  `#FF9595 #F9BC0B #FBF078 #CBFB91 #B5CEF6 #D7B1F9 #E6C9A8 #FFFFFF #282828 #F12424 #FF6821 #F5D107 #009300 #3737F4 #4A0081 #61D2BA #65C444 #90949D #FFD9E9 #FAE3CE #CDF0EB #D9E8FF #D4CDF0`
  第 8 项 `#FFFFFF` 在弹窗里**不显示**（它落在第 1 列图标的那个位置），所以界面上看到的是 22 个
- 复现办法（下次不用重新摸索）：读运行中的 `desktopcal` 进程内存（`OpenProcess` + `VirtualQueryEx` + `ReadProcessMemory`）搜连续 COLORREF，在 `0x04261514` 命中 → `EnumProcessModulesEx` 算出它属于 `dkappcal.dll` + RVA `0x211514` → 去磁盘同一偏移读，字节一致
- **踩过的坑（别再踩）**：第一次扫 DLL 是按 **22 项**去搜的，漏了那个 `#FFFFFF`，序列对不上所以 0 命中，于是错误地判断"文件里没有清单、只能靠截图像素"。**搜连续数组前先把项数确认对**
- 弹窗布局：8 列 × 3 排，前两排第 1 列是「清除」∅ 和「调色板」两个图标，所以前两排各 7 个色、第三排 8 个
- 另外：`comdlg32.dll` 确实加载在 `desktopcal` 进程里 → 那个「更多颜色」对话框就是系统的 `ChooseColor`，不是它自己画的
- **坑：`res.xml` 那组有 14 个，但 `#666666` 不在日格调色板里**——"备注编辑器的文字色"和"日格调色板"是两套表，别混
- **底色在库里就是它色板的原值**：`it_bgcolor` 存的是 BGR 小写串（`#FF9595` → `'9595ff'`，`#F12424` → `'2424f1'`）。用户手点的两天正是这两个值，说明"点色板 → 存这个串"这条路是通的。`to_bgr()` 现在输出**小写**，好让"我们写的"和"它写的"逐字节一样

**色板之外**
- 下面一行：hex 输入（`#RRGGBB`，即时生效、撞色给红字）+ 竖线 + 归档释放出来的颜色（最多 5 个）
- 允许任意 hex：色板只是"跟它对齐的快选"，颜色身份仍按字符串算，不影响占用 / 租期那套逻辑
- **它那个「调色板」图标打开的是 Windows 自带的 ChooseColor 对话框**（comdlg32，不是它自己画的；连标题 "Color" 都是英文的，跟中文界面不一致）。字段是 **Hue/Sat/Lum（0–239/0–240）+ Red/Green/Blue（0–255），没有 hex 输入框**。所以：
  - "在 DesktopCal 里直接输颜色代号"这件事**不存在**（用户最初的抱怨是对的）
  - **任何 RGB 都是可达的**（在那个平面/数字框里配出来），只是没法用 hex 精确复现，得敲 RGB 三个数
  - 所以对齐色板解决的**不是"能不能选到"，是"能不能在两边同一个位置找到同一个颜色"**
- **48 格系统基本色和快选盘 22 色交集 = 0**（48 格里只有 47 个不同值，`#400040` 出现两次）。两套不重叠但有几对很近：`#4A0081`/`#400080` 差 10、`#FBF078`/`#FFFF80` 差 17.5、`#009300`/`#008000` 差 19 —— "看着一样、其实是两个值"比明显不同更危险，别把两套混着摆
- 那个对话框下面还有 16 格「Custom colors」会记住用过的自定义色。我们**没有照抄这个**：那个列表只会摆出已经被占用的颜色（见 §5 的「归档释放色」）

## 5.5 写穿同步：登记表 → 桌面日历（本轮新增）

**分工**：`desktopcal-colors.json` 是**意图**（哪件事、什么颜色、截止哪天）；`calendar.db` 是它的**投影**（截止日那天的倒数日 + 底色）。

**链路**（`panel/projection.py` + `server.py`）：
- 面板点「确认」→ `POST /api/data` → 先 `dump()` 登记表 → **立刻** `projection.apply(items, removed=本轮删掉的)` 写 calendar.db
- **落盘时机**：「确认 / 删除」是**立即** POST（实测点下去 1ms 就发出），只有拖排序留 500ms 防抖。所以"点完确认马上关 DSH"也不会丢
- 右上角「重启并同步日历」→ `POST /api/sync` → 全量投影 + `restart_calendar()`。**它不负责保存**：数据在点确认时就写完了，这一步只是让桌面日历重读一次库（DesktopCal 只在启动时读库）。按钮的 `pending` = "库里改过、日历还没重启"，是提醒不是提交
- `GET /api/busy` → `{项目名: [有安排的日期]}`，面板据此禁日期

**身份 = 行内文字颜色（用户定的唯一标准）**
- 颜色存在 `item_table.it_content` 里，**逐行**包成 `<font color="#RRGGBB">正文</font>`，多行用 `\r\n` 连接；没有单独的颜色列。很好查：扫描一遍按颜色聚合即可
- 一行有没有颜色 = 它属不属于某个项目。**颜色唯一 ↔ 项目唯一**（登记表保证在役项目颜色不重复）
- `-ds` 尾巴**不再是归属依据**。它是贴在正文后面的，拿它当依据有把人工编辑内容一并删掉的风险（用户明确指出）。现在 `-ds` 只留在我们自己建的倒数日标题上，仅作"这条是 DS 建的"的弱提示
- **同步永不修改 `it_content`**：只写 `event_table`（我们建的倒数日）和 `it_bgcolor`（当天底色）。所以常规同步不可能吞掉人手写的内容。两个例外，都是用户明确要求的：
  1. **改项目颜色**时把该颜色所有行的 `<font color>` 换掉——只改属性，不动正文
  2. **删除条目**时把该颜色真正的文字行整行删掉（见下面「删除」那条）
- `/api/busy` 返回 `{busy: {颜色: [有安排的日期]}, bg: {日期: '#RRGGBB'}}`：
  - `busy` → 早于"最后一条安排"的日期禁选
  - `bg` → **一天只能铺一个底色**，已经被别家颜色占掉的日子也禁选（悬停提示"这天已经铺了「xxx」的底色"）
  - 当前值本身永远豁免（否则那个日期会在日历上凭空消失）

**删除条目会连带清掉什么**（用户 2026-11-25 定的）
- 以前只清倒数日和底色，日格里带这个颜色的**文字行会留着**。后果实测复现过：同色被下一个条目拿走时，那些残留文字会被认领——`busy_map` 把上一个项目的日子算成新项目的，改颜色时还会被一起重绘
- 现在删除是**三个都清**：倒数日 / 当天底色 / 该颜色的文字行（`_drop_text_lines`）。只删 `after`（上一任交还日）之后的行，归档那一任的文字不动
- **交还记录**：删除会往 `~/.dsh/state/desktopcal-released.json` 写一条 `{name, color, day: 删除当天}`。`_handback_day()` 现在同时读归档和这份记录，所以被删掉的颜色的租期也能正确切分
- `/api/data` 的 `released` 合并两个来源：归档（`how="archive"`）/ 删除（`how="delete"`），按日期倒序、跳过还被在役条目占着的，最多 8 条，前端取 5
- **删除必须弹窗手打 `delete` 才执行**（正文会被真删，不可撤销）。空输入、打错、只打 `dele` 都点不动「删除」；大小写和首尾空格不管

**颜色租期：同色回收再用怎么办**（用户提出的问题，已实现）颜色是会被回收的：条目归档后颜色释放，下一个条目拿走。所以"某颜色的某一行属于谁"必须按租期切分，不能只看颜色：

```
小程序上架 #722F37 截止 2026-11-20  →  归档，颜色释放
读书      #722F37 12-01 ~ 12-10 的行  →  全在交还日之后，归读书
```

规则（`projection.color_owners()`）：
- `current[颜色]` = 活跃文件里持有该颜色的条目
- `prev_max_deadline[颜色]` = 归档文件里同色条目的**最大截止日**，也就是上一任的交还日
- 判定一行：颜色没有活着的持有者 → 忽略；日期 **≤ 交还日** → 算上一任的，忽略；否则算当前持有者的

实测（在库副本里塞一条 11-15 的同色行）：11-15 被正确排除，12-01 仍在。

**改颜色时的重绘也必须按租期切开**（用户追问的点）
从"粉"改成"蓝"时，如果按颜色全量重绘，会把**已归档条目租期内的同色行**一起刷掉。所以 `projection._repaint(cur, old, new, after)`：
- 只重绘日期 **> 交还日**（`_handback_day(old)`）的行
- 只改 `<font color>` 属性，正文一个字不动
- 旧颜色的底色同样只在租期内清（`_clear_color_bg(..., after=)`）

实测：读书 10 行 `#722F37 → #123456` 全部重绘；伪造的 11-15（归档租期内）保持 `#722F37` 没被碰。

**前提：改颜色必须走面板。** 直接手改 JSON 不会触发重绘，颜色就换了但行还是旧的（今天 11-25 上那坨残留底色就是这么来的，已手动清掉）。

**投影规则**（`projection.apply`）：
| 情况 | 做什么 |
|---|---|
| 截止型 + 有截止日 | **先撤销**：把本颜色租期内、不在目标日的那条倒数日删掉 → **再设置**：补/改目标日那条，底色铺到那天 |
| 非截止型 / 没有截止日 | 删掉本项的倒数日，清掉本项颜色的底色 |
| 改名 | 倒数日标题原地改（`title.split(" -ds")[0]` 对比项目名） |
| 改颜色 | **先撤旧**：删掉旧颜色租期内的倒数日 + 底色 → 再把租期内的文字行重绘成新色 |
| 被删除的条目 | 按 `removed` 里的名字+颜色清它的倒数日 + 底色 |
| 孤儿投影 | 带 `-ds`、日期在今天之后、颜色已无人持有的倒数日 → 删（`_gc_countdowns`） |
| 底色清理 | 靠颜色唯一性 + 租期：本颜色只该出现在自己的截止日，别处同色底色清掉 |

**倒数日怎么认归属**（踩过的坑）：不能只看 `-ds:<名字>` 尾巴——早期命令行建的那条只有裸 `-ds`，改期时它就成了漏网之鱼，和新倒数日并存。现在的判定是「**颜色匹配 + 在租期内 + 看起来是我们建的**（正文含 `-ds` 或标题正好等于项目名）」，颜色和名字都不依赖单一标记。

**写 `ev_content` 要转义**：`calendar.db` 里事件正文存的是转义形态（`|&lt;|font color=...`），而 `desktopcal.add_event()` 写的是未转义的。所以 `_add_countdown` 建完会再 UPDATE 一次成 `enc(paint(...))`，否则可能显示成字面 `<font>` 标签。

安全：每次写库前 `dc.backup()` 存一份；`apply(dry=True)` 会把库复制到临时文件再跑，真实库不动（用来验证规则）。

**禁日期规则**：`minIso = 该项目最后一条安排`；日历里 `iso < minIso` 的日期渲染成不可点的斜纹格子，标题栏显示「最早 xx/xxx/xxxx」。原理：截止日早于已有安排 → 那些安排就被甩到截止日之后了。

**重启为什么不由插件发起**：插件 spawn 出来的进程会跟着 DSH 一起退。所以按钮只做「同步 + 正常关闭」，用户自己点桌面图标打开 —— 这样新进程是用户发起的。

**坑：`CloseMainWindow()` 关不掉它。** `desktopcal.exe` 是贴在桌面上的常驻程序，**没有主窗口**（`MainWindowHandle = 0`），那个 API 直接返回 `False`、什么都不做——这就是"点了重启并同步日历但没生效"的真正原因（当时的写库其实成功了，只是软件没重启，看到的还是旧画面）。
正确做法：枚举该进程的窗口，找类名 `xUIWindow`、标题以 `dkcexe_framework` 开头的那个（它有 19 个隐藏窗口，只有这个是框架窗口），`PostMessage(h, WM_CLOSE=0x0010, 0, 0)`。

**重启是"关 + 开"两步，别只写关闭**（踩过）：
1. 关闭：上面的 WM_CLOSE，然后轮询等进程真的退出（最多 6 秒）
2. 启动：`explorer.exe "<APPDATA>\CalendarTask\desktopcal.exe"` —— **必须走 explorer**，这样新进程挂在资源管理器下，不挂在 DSH 的进程树上，DSH 退出不会把它带走（用户明确提过这个担心）；插件自己 spawn 的会跟着 DSH 一起死
3. 全程 `creationflags=0x08000000`（`CREATE_NO_WINDOW`）+ `-WindowStyle Hidden`，否则会闪一个控制台黑框

实现见 `projection.restart_calendar()`，返回值形如 `"closed / restarted"`、`"not-running / restarted"`、`"closed / restart-failed"`。

**关不掉/起不来时不清 pending**：`/api/sync` 只有在返回值以 `restarted` 或 `running` 结尾时才清标记，否则保留，让用户能再点一次。

**按钮什么时候可点**：服务端有个 `state/desktopcal-pending.json` 标记。`POST /api/data` 只要这一轮真的动过日历库（`added` / `events_removed` / `cleared_bg` / `removed` 任一非空）就写这个标记，`GET /api/data` 返回 `pending`，面板据此启用按钮；`POST /api/sync` 成功后删标记。所以**没改动时按钮是灰的、点不动**，纯排序也不会让它亮（排序不动日历库）。按钮样式是 `data-v="danger-outline"`：红字红框，禁用时转灰。

**坑：面板服务被重复拉起了 9 份**。Windows 的 `SO_REUSEADDR` 允许两个进程绑同一个端口，请求落到哪份代码不确定（改完代码不生效就是这么来的）。现在 `server.py` 用 `allow_reuse_address = False`，第二个实例直接 `WinError 10048` 退出。

## 8.5 反向同步（设计中，还没做）

**为什么**：现在只有"推"。用户手写在日历里的文字、手涂的底色、在日历里建的提醒，面板全不知道。严格说这不是同步，是单向投影。

**已经搞清的事实（2026-11-25 实测，用户配合改了三天）**
- `it_mdate`（日格）和 `ev_mdate`（事件）**DesktopCal 确实会维护并更新**
- **改文字颜色 → `it_mdate` 变**：11-27 那行从 `09:12:52` → `18:31:21`
- **设底色 → 建新行**：11-28 原来没行，设完出现 `cdate = mdate = 18:36:51`。所以"只改底色"也会写 mdate（那行是新建的，没法证明"改已有底色"也更新，但至少写入一定带 mdate）
- **改事件颜色 → 整条换掉**：11-30 那个提醒 `ev_id` 从 **24 变成 25**，`ev_cdate` 保留原值（02:39:28Z），`ev_mdate` 更新到 10:31:01Z。**→ 事件不能用 `ev_id` 追踪身份，得按「日期 + 内容」配**
- 格式：`it_mdate` 是本地 `YYYY-MM-DD HH:MM:SS`（跟我们写的格式一致，能直接比）；`ev_mdate` 是 UTC `...Z` 带微秒
- **别用 `it_mtime` / `ev_mtime`**：那个整数列值很乱（`0`、`1`、epoch 混着），不可靠，只看 `mdate`

**范围（用户定的）**：无颜色的内容 = 默认内容，插件**不主动写**、也不当成数据。抓取只认"带颜色的行"。

**触发时机（用户要的"触发式"，不做轮询）**
- 面板挂载
- **窗口重新获得焦点** ← 最容易漏：用户去日历改完切回 DSH
- 保存前预检（发现日历被动过就提示，别盲写覆盖）
- 点「重启并同步日历」之后
- 面板服务启动
- 容易漏的边界：桌面日历重启后、机器休眠唤醒后（"今天/租期"要重算）、长时间开着不动（距上次拉取超过 N 秒再交互就重拉）、切到「已归档」页（那页数据是单独拉的）

**形态**：差异清单 + 手动采纳，三个集合。**永远不自动合并正文**，跟删除要打 delete 一个思路。

**后端已实现（2026-11-25）**：`projection.drift()` + `GET /api/drift`（只读，不改任何东西）

| 桶 | 意思 | 判定 |
|---|---|---|
| `missing` | 登记表里有、日历上找不到它的投影 | 按「颜色 + 类型3」找事件，日期对不上就查有没有同色事件；没有就是 missing。带 `reason`：快照里有记录 = `deleted`（我们写过，被删了）；没有 = `never-synced` |
| `changed` | 投影还在但被改了 | 同色事件在**别的日期** → `what:"event"`；事件对但那天底色没了/换了 → `what:"bg"` |
| `unowned` | 日历上有颜色内容、可那颜色不归任何在役条目 | 事件 / 日格文字 / 底色 三类都扫，`kind` 区分 |

外加 `~/.dsh/state/desktopcal-projection.json`（`_snapshot_write`，每次 `apply()` 成功后写）——只记登记表里那些条目应该有的投影，**用户自己涂的东西不进快照**。没它的话分不清"我们写过、被删了"和"从没写过"，就无法避免"一点同步就把用户故意删掉的又复活"。

**实测（用户真机数据）**：登记表空、日历上有他自己的 7 处带颜色的东西，`drift` 正好报 7 条 unowned（11-27 文字 `#D9E8FF`、11-28/12-07/12-17 三处底色、11-30/12-07/12-17 三个事件）；建一条 2027-05-20 的测试条目后 missing/changed 都是 0；把它的倒数日删掉 → `missing` 且 `reason:"deleted"`；把那天底色改成别的颜色 → `changed` 且 `what:"bg"`。测完已清理，日历回到"只剩用户自己的 7 处"。

**UI 已做（2026-11-25）**：面板顶部一条窄提示条「日历上有 N 处变化 / 查看」，点开展开分组，每组每行带一个颜色小方块：
- `missing` → 「读书 · 倒数日被删了 · 应在 12/Dec/2026」（`reason` 决定措辞：被删 / 还没同步过）
- `changed` → 「读书 · 倒数日被挪到 X（应在 Y）」或「那天 Y 的底色没了或被换了」
- `unowned` → 「文字 · 27/Nov/2026 · 写成插件的第一次测试」，如果这个颜色曾经属于某个条目，后面追加「（原来是「X」的，已删除/已归档）」
- 有 missing/changed 时底部出「按登记表补回投影」→ `POST /api/repair`（只补投影、不重启日历）

**unowned 的来源分类**（用户要的）：`projection._ever_owner()` 把归档表 + 释放记录合成 `{颜色: (名字, "archive"/"delete")}`，同色优先取删除那条。这样能区分"用户自己涂的"和"删掉/归档的条目留下的"。

**自动收进登记表（2026-11-25，用户定的）**：`POST /api/adopt`
- 用户的原话：「如果没有冲突的话，就自动收进去呗。同步本来就应该是默默进行的」 → 所以挂载时和窗口 focus 时都自动调
- 规则：把 `unowned` 按颜色分组 → 有带标题的事件就建 `project`（deadline = 事件日期），有带文字的颜色行就建 `ongoing`；只有底色、没有名字的**不建**（认不出是哪件事）
- **安全阀**：每个候选都先在**库副本**上 `apply(dry=True)` 跑一遍，只要会产生任何改动（`added` / `cleared_bg` / `bg_changed` / `events_removed` / `text_dropped` / `repainted`）就**不收**——因为"收进来"等于改用户自己的日历。收不了的留在提示条里当冲突
- 实测（用户真机 7 处）：自动收进 **1 条**（11-27 那行文字 → `ongoing`）；剩下 6 条都被安全阀挡下：3 条只有底色（没名字）、2 条事件收了会把它那天的底色换掉（`#FFE4E1` vs 现有 `#FF9595`）、1 条是提醒（收了会平白多一条倒数日）

**"底色和事件颜色对不上"的根因（2026-11-25 查清，是测试数据不是 bug）**
- 投影**永远**让两者相等：`_reconcile_countdown` 用项目色画事件文字，`_set_bg(截止日, to_bgr(项目色))` 用同一个色铺底。代码里没有第二种路径
- 之前那几处不一致全是**手动改出来的**：底色 `#FF9595` / `#F12424` / `#90949D` 是 DesktopCal 调色板里的色（手点的），事件色 `#FFE4E1` / `#FFC0CB` / `#40E0D0` **根本不在 22 色和 48 格里**（第 3 个甚至是自定义青绿）——两处是分两次手设的
- 重测（清空后）：建一条 `#D7B1F9 @ 2027-03-15` → 事件色 = 底色 = `#D7B1F9`，`drift` 全 0；手动把底色改成 `#65C444` → `drift` 立刻报 `changed what=bg`；点「按登记表补回投影」→ 又一致、`drift` 归零
- **结论**：`drift` 里出现 `changed what=bg` 就等于"有人手动改过那天的底色"，不是系统产生了不一致

**保存前预检（2026-11-25）**：`save()` 里先 `GET /api/drift`
- `missing` / `changed` 都为空 → **静默保存**（用户要的）
- 有冲突 → 弹「日历那边有变化：日历上 N 处投影不见了、M 处被改过。现在保存会按登记表把它们覆盖掉。」[先看看] / [仍然保存]；选「先看看」会 `load()` 回到服务端真实状态
- 已知小瑕疵：`confirmEdit` 是先关卡片再 `commit`，所以弹窗出现时卡片已经关了。功能没问题，观感可以再调

**踩到的坑（很重要，已经修）**：`_set_bg` 以前不管旧值是什么都直接 UPDATE，而且**不报告**——于是"把某天底色换成另一个颜色"这件事在 `report` 里完全看不见，`adopt(dry=True)` 的安全阀就漏过了它。结果我第一次跑 adopt 时，把用户 12-07 的 `#FF9595` 改成了 `#FFE4E1`、12-17 的 `#F12424` 改成了 `#FFC0CB`。
现在 `_set_bg` 返回布尔（把非空旧色换成别的才算改），`report["bg_changed"]` 计数，`adoptable()` 也会看它；同值直接跳过（不再反复蹭 mdate）。两处底色已还原，那两条误收的条目已撤销。

**⚠️ 测出来的一个真实危险，记住**：把一个**正在被用户使用**的颜色登记成条目，等于"认领"了日历上所有这个颜色的内容；之后删掉这条条目，`_clear_color_bg` / `_drop_text_lines` 会把用户那些内容一起清掉。我测试时用 `#90949D` 建了一条临时条目，结果把用户 11-28 的底色清空了（已恢复）。→ **将来做 unowned 的「收进登记表」动作时，必须先提示"这会认领 N 处已有的内容"**。

**踩到的真 bug（顺手修了）**：`it_content` 有两种形态——我们自己写的是**原始** `<font color="#...">`，DesktopCal 自己改过的是**转义**形态 `|&lt;|font color=|&quot;|#...`。原来的 `LINE_COLOR` 只认原始形态，SQL 过滤也只 `LIKE '%<font color=%'`，于是**用户在日历里改过颜色的那行，`busy_map` 根本看不见**（会导致面板以为那天没安排，把截止日缩到它前面）。现在三处（`busy_map` / `_drop_text_lines` / `drift`）都改成先 `dc.dec()` 再匹配，SQL 两种形态都认。实测：把 `#D9E8FF` 临时登记成在役色后，`busy_map` 能返回 `{'#D9E8FF': ['2026-11-27']}`（修复前是空）。

## 8.6 防 DSH 误操作（P0 已做）

前端那些限制对 DSH 一条都不生效——它走 CLI 直接 SQL。所以硬约束要下沉到 Python 层：

| 保护 | 位置 | 行为 |
|---|---|---|
| 删到用户内容要拦 | `cmd_del_day` / `cmd_add_day --replace` | 列出不是本插件写的行并拒绝，`--force` 才清 |
| 登记表变空要拦 | `projection.apply()` | 登记表空、又没传 `removed`、库里还有我们建的未来倒数日 → 中止并报错（`force=True` 才能过） |
| 原子性 | `server.py` POST | 先投影成功**才** dump 登记表；投影被拒返回 409，不留"JSON 写了但库没动"的半截状态 |
| 审计日志 | `dc.audit()` | 每条写操作一行到 `~/.dsh/state/desktopcal-audit.log`（CLI 所有写命令 + apply） |
| 恢复前备份 | `cmd_restore` | 本来就有 |

**P1 已做（2026-11-25）**
- 新增 `guard.py`（技能根目录）：`validate()`（名称必填 + 撞色）、`color_owner()`、`check_color_registered()`、`is_expired()`。**规则只有这一份**，`panel/server.py` 的 `_validate` 和 `desktopcal.py` 的写命令都调它
- CLI 现在写带颜色的东西前会查「这个颜色有没有主」：`add-day --color` / `set-bg` / `add-countdown --color` / `add-reminder --color`。没主就拒（`--force` 才过）
- `set-bg` 还查「这天是不是已经有别的底色」，有就拒（`--force` 才覆盖）
- `guard.today()` 每次现算，避免服务开几天之后"过期"判断失真

**"收敛到 apply()" 只做了一半，原因得说清**：CLI 写的是**登记表之外**的内容（随手一行文字、一个临时底色），而 `apply()` 只管登记表里那些条目的投影。要真把 CLI 收敛进 `apply()`，前提是**登记表成为所有内容的唯一真相**——那是一次数据模型改造（每条随手写的文字都得有归属），不是补几个检查能完成的。现在的折中是：**CLI 写之前必须过同一套校验**，写完不调 `apply()`，两边不会互相打架。

**真正的弱点**：以上全是"走 CLI 才有"的约束。DSH 只要绕过 CLI 直接 `sqlite3` 写库就全部失效。SKILL.md 里写死了禁令，但那只是自觉，不是硬约束。

### 两处修复（2026-11-25，用户拍板修的）

**1. 空行不再积——`projection._set_bg`**
DesktopCal 的格子是**按行**存的。"铺底色 → 清底色"之后会留一条内容空、底色空、`it_history` 为 `[]` 的行，一直积在库里。现在清底色时若这行正文也空、`it_history` 也空，就**整行删掉**；有 `it_history`（说明用户在 DesktopCal 里编辑过这一天）一律保留。另外"清一个本来不存在的格子"以前会 INSERT 出一条空行，现在改成什么都不做。
实测：建 2027-07-01 项目再删掉 → 库里没有残留行；手工造一格"有正文 + 有底色"的，清底色后正文一个字都没少。

**2. 过期截止日不许新建——`guard.validate`**
截止日早于今天 → 409「「X」的截止日 YYYY-MM-DD 已经过去了，截止日不能早于今天」。以前会被接受、铺上底色、建倒数日，然后下次 `GET /api/data` 时 `tidy()` 把它归档，下一次 `apply()` 又把投影撤掉——用户看到的是"我刚建的就自己没了"。
**例外**：已经躺在登记表里、只是"过了一夜变过期"的条目，原样提交不拦（`validate(items, current=...)` 比对名字+颜色+截止日）。不这么留口子，午夜过后整个面板会被这条过期记录的 409 卡死。

## 8.8 认领：日历上没颜色的内容 → 归到某个事项（2026-11-25 做的）

### 为什么需要它

面板的模型是"一件事一个颜色"，正文明明躺在日历里，但只要**没有颜色**就对不上任何项目——`drift()` 的"无主"桶只收**有颜色**但没主的东西。结果是：用户日历里已有的内容（Erasmus、Europass CV 那些）在面板里完全看不见，像插件瞎了一只眼。用户选了"允许认领成项目"（另外两个选项是只读列出、保持现状）。

### 语义（改动日历里已有正文的唯一入口）

| 项目 | 做法 |
|---|---|
| 粒度 | **行**。颜色是行属性（`<font color>` 包住一行），所以认领一行而不是整天 |
| 目标 | 必须是**在役项目**的颜色（`color_owners()[0]`）；没项目就先建 |
| 动作 | 给那一行套上 `<font color="#XXXXXX">…</font>`，正文一个字不改 |
| 后果 | 从此这行归那个项目：换色时跟着重绘（`_repaint`），**删项目时跟正文一起删掉**（`_drop_text_lines`） |
| 警告 | 展开区顶部那行小字写死："归了之后，删那个事项会连这行正文一起删掉"（用户要直接拖，所以不做弹窗） |

### 接口

- `GET /api/plain` → `{ok, days: {"2026-11-25": ["watch Erasmus video", …]}}`
  `projection.plain_days()`：只列**一个颜色都没有**的行。已经带颜色的行不在这里（那种归谁由租期决定，已经在别的栏目里体现）。
- `POST /api/claim` ← `{claims: [{iso, text, color}]}` → `{ok, claimed, failed}`
  `projection.claim(iso, text, color)`：只认领"文字逐字相同、且完全没颜色"的那一行；认不到就什么都不改（重复点不会套两层 `<font>`）。

### 两道拒绝（都测过）

1. 颜色没有主人 → 「颜色 #XXXXXX 现在没有主人，先建一个事项」。
2. 租期对不上 → 同色被归档条目用过时，`prev_max_deadline` 之后才算当前持有者的；认领落在上一任租期里会被拒（否则这行算不进"这个项目的安排"，`busy_map` 看不见它）。

### 面板（client.js）——用户定的样子，别改回去

- 名字叫**未分类**（不叫"日历上还没归属的内容"）。
- 它长得**跟别的事项一模一样**：一个普通行，前面那个色块是空的（`.ctp-chip-empty`），中间写"未分类"，右边是条数。
- 展开才看得见里面：**一条一行，左内容是事项名、右是它自己的日期，不按日期分组**（用户明确说"不用聚类"）。每行左边有个细把手（一直淡显，悬浮加深）表示"这条能拖"，行与行之间有 1px 分隔线。
- 提示文字就是用户给的那句：**拖动item进入事项进行分类**（已归档那一页换成"这些都是过去日子的内容，要归类请到「进行中」里拖"——那儿拖不动，照搬会骗人）。
- **不点色块归类，改成拖动**：因为种类一多色块排不开。拖一行到上面任意事项的行上，就归它。
- 两个标签页里都有未分类：今天及以后的行在"进行中"，过去的行在"已归档"（按日期分，跟归档本身的含义对齐）。
- 拖的时候按"有效期"判断能不能收：有截止日的事项只管到截止日那天为止，**收不下的行拖过去那个事项变灰**（`.ctp-row[data-nodrop="1"]`），已归档的事项一律变灰（颜色已经释放了）。
- 没有二次确认弹窗（用户要的是"直接拖动"），代价写在展开区顶部那行小字里："归了之后，删那个事项会连这行正文一起删掉。"

### 四个真问题（①②④ 已修，③ 只改了文档）

1. **✅ 已修（2026-11-25）——过期条目的投影不会被清（⑤⑥）**：条目过期归档后，它在日历上的倒数日和底色**留在原地**。`tidy()` 只动登记表，不通知 `apply()`；drift 会把它列成"无主的颜色（已归档）"，而面板上的「按登记表补回投影」会被防误删保险拦下（409「登记表是空的，但日历里还有 N 条倒数日」）——因为那时登记表确实是空的。**结果：过期项目的倒数日会一直挂在桌面上，除非有人拿走那个颜色。** 建议：归档时把它当作 `removed` 跑一次投影，或者让 repair 在这条上放行（只清"已归档/已删除"名下的）。
2. **✅ 已修（2026-11-25）——双窗口丢更新（⑦）**：面板保存 = 把整份 `items` 覆盖写回。两个窗口各拿一份快照，后保存的吃掉先保存的，**没有任何提示**（冲突弹窗只比日历，不比登记表）。建议：POST 带一个 `rev`（或基准内容哈希），服务端发现基准变了就 409，让面板走"重新加载还是覆盖"的询问。
3. **日期卡的键盘是假的（⑧）**——只改文档，功能没做：`DateCard` 的 `STEP` 只改 `view.d`，而渲染根本不用 `view.d`；也没有 Enter/空格选中。第 175 行那段文档（"←→↑↓ 移日、Enter/空格选中"）是错的。要么补实现（用 `view.d` 画一个焦点框，Enter 调用 `onPick(view.d)`），要么把文档改掉。
4. **✅ 已修（2026-11-25）——确认保存时卡片先收起、冲突弹窗后出现**：见下面「三条修复」。

### 三条修复（2026-11-25）

**① 归档时收投影——`projection.retire(items, prior)`
`tidy()` 把过期条目挪进归档之后，调 `retire()` 把它们的**倒数日**和**租期内的底色**收掉。
关键是 `prior`（交还日）必须在**挪进归档之前**算：挪完再算，`prev` 就成了它自己的截止日，`_clear_color_bg(after=hb)` 会把"它自己的那一天"也跳过去（第一版就是这么漏的，测出来了）。
跟删除的区别：**不删正文**。用户写在那几格里的字留着，之后在「未分类」里还能看到。
实测：建 2027-06-06 截止 + 2027-06-07 一行带色正文 → 把截止日改成昨天模拟过期 → GET 一次 → 倒数日没了、底色清空、那行正文还在。

**② 并发写保护——`rev` + 409
- `GET /api/data` 多返回 `rev` = 登记表文件的 sha1 前 16 位。
- `POST /api/data` 收 `baseRev`；和服务端当前 rev 不一致（且没传 `force`）→ 409 `{conflict:"registry", rev}`。
- 面板保存时带 `baseRev`；收到 409 就弹「另一个窗口改过登记表」，两个出口：**重新加载**（丢掉本地改动）／**覆盖它**（带 `force` 再存一次）。
- 不传 `baseRev` 的调用方（CLI、别的脚本）行为完全不变。
实测：拿旧 rev 保存 → 409 → 弹窗 → 「重新加载」看到对方那条；「覆盖它」保存成功、卡片收起、提示"已保存"。

**④ 卡片等保存成功再收起**
`closeOnSaved` ref：点「确认」时只置位，不立刻 `closeEdit()`；`save()` 成功后才关（`setOpen(null)` 等）。
冲突时卡片保持展开 —— 现在弹窗出现时卡片还在后面开着，不再是"什么都没点它自己弹了个框"；点「先看看」卡片也留着，用户可以接着改。
实测：确认 → 弹窗 + 卡片仍开 → 先看看 → 弹窗关、卡片仍开 → 确认 → 仍然保存 → 成功后才收起。

### 插件市场报「包元信息错误」（2026-11-26，已修）

症状：市场里 `@local/dsh-calendartask` 没有名字/描述，只有一行

```
包元信息错误：Plugin metadata for @local/dsh-calendartask: Error: ...locale\en.json:
SyntaxError: Unexpected token '﻿', "﻿{ "meta"..." is not valid JSON
```

原因：`locale/en.json`、`locale/zh.json` 从 v1 第一个提交起就带着 **UTF-8 BOM**（`EF BB BF`）。
DSH 读元信息走 `readPluginMeta()` → `JSON.parse(readFileSync(file, "utf8"))`，**不剥 BOM**，
于是 `dictionariesOf()` 读到第一个语言文件就抛错，整条元信息（标题 / 描述 / 图标）退回
`{ error: "Plugin metadata for ..." }`。坏的只是市场里那一栏：插件本身照常加载，`list_plugins` 里
`include:calendartask` 一直是 `active`。

修（`ffceeae`）：两个文件去掉 BOM；`tests/run.py` 开跑第 0 步检查 `package.json` + `locale/*.json`
——开头不能有 BOM、必须能 `json.loads`，坏了直接 FAIL。

记住：Windows 上 PowerShell 5.1 的 `Set-Content -Encoding utf8` 会悄悄加 BOM，改这类文件用编辑器或
`UTF8Encoding($false)`；市场那栏是每次现读（`readPluginMeta` 没有缓存），文件改好后刷新页面即可。
